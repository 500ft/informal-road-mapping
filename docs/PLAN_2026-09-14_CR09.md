## The defect, as measured

CR-R03c found that every **curved** corridor passes the component layer and fails
the exported line, because `extract_candidates` delivers one straight
`endpoints_px` chord per component ([record](../results/extractor_stress_cases.json)):

| case | component recall | exported-line recall / precision |
|---|---:|---:|
| low_snr (curve) | 1.00 | 0.11 / 0.11 |
| tight_curve (hairpin) | 1.00 | 0.25 / 0.26 |
| demo_reference | 0.92 | 0.44 / 0.45 |
| wide_corridor (straight) | 1.00 | 1.00 / 1.00 |

The representation is wrong, not the threshold. A chord is exact only for
straight corridors.

## Task 1 (Agent, P1, ~3 h) — `path_px`: a centred polyline through each component

**Finish line:** the three curved cases pass the line layer (`line_ok`) while the
three straight cases keep line recall 1.00; the component layer is numerically
unchanged; the v1 baseline record is byte-unchanged.

Ladder, in order:

1. *Does it need to exist?* Yes: CR-R03c's finding; three tests currently pin the
   failure as observed behaviour and will be updated, not deleted.
2. *Already here?* `label_candidates` (PR #15) already gives the component pixels.
   `rasterise_segments` already scores a list of segments; a polyline is a list of
   segments.
3. *Stdlib / installed dependency?* `scipy.ndimage.distance_transform_edt` and
   `scipy.sparse.csgraph.dijkstra` are already installed (scipy is a core
   dependency). No scikit-image, no networkx.
4. *Minimum that works:* for each surviving component, build the 8-neighbour graph
   of its pixels with edge cost `1 / edt(pixel)` so the cheapest route hugs the
   medial axis; take the two mutually farthest pixels (two Dijkstra sweeps, the
   tree-diameter trick); the shortest path between them, **subsampled every 4 px
   with both ends kept**, is `path_px` (list of `[x, y]`).

Contract:

- New field `path_px` on every candidate. `endpoints_px`, `length_px`,
  `width_px`, `orientation_deg`, `elongation` **stay exactly as they are** so
  `results/method_demo_synthetic.numeric.json` and its four tests are untouched.
- `to_geojson` emits `path_px` as the LineString coordinates.
  `test_geojson_shape` changes from `len(coords) == 2` to `>= 2`.
- `stress_cases.score_lines` rasterises `path_px` (consecutive pairs) instead of
  `endpoints_px`. The three negative-control tests that overwrite `endpoints_px`
  overwrite `path_px` instead.
- `demo_synthetic.py` plots `path_px`; the figure is regenerated from its documented
  source (allowed by CONTRIBUTING; the numeric record, not the PNG, is the test).
- `results/extractor_stress_cases.json` becomes **schema v4**, `supersedes` names v3
  and states the line layer now scores `path_px`. The v1 baseline file stays
  byte-identical and `test_baseline_record_is_preserved_unchanged` keeps passing.
- Mark the 4-px subsample with `# ponytail: fixed 4-px subsample; Douglas–Peucker
  when someone needs fewer vertices`.

Tests to update (all in `analysis/tests/test_stress_cases.py`), stating the new
